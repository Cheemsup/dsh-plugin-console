# dsh-plugin-console 下一阶段方向：从「插件地图」到「插件运行控制台」

> 目标读者：本插件的维护者与设计者。
> 本文回答两个问题：**用户对一个插件能看到的信息够不够？** **能不能简单查看、甚至控制 DSH 内部插件的运作？**
> 结论先行：现状在「这个插件从哪来、模型看到什么」上已经很强；缺的是「它最近做了什么、现在健康吗、动它会怎样、动完怎么撤回」。建议补三层：**轨迹层（行为）→ 影响层（what-if）→ 杠杆层（分级控制）**，并把全局变更继续交给 `pluginManager`，插件控制台只做解释、观测与可撤销的会话级调节。
>
> 如果只做三件事：**用 session log 做插件活动；用现有快照做影响预览；用现有 `materializeRecipe` 做会话贡献掩码。**

---

## 1. 现状：强在解释「构造」，不在观察「运行」

五个视图各自回答一个构造问题，这一点做得很好：

| 视图 | 回答的问题 | 数据基础 |
|---|---|---|
| 插件 | 这台机器装了什么、都在干什么 | Loader 条目、bundle 层、patch 覆盖、fiber 副作用 |
| 会话 | 这个会话的插件是哪来的 | header、preset 声明、运行时组合 |
| 工具 | 模型能看到哪些工具、谁给的 | `tools.view()`、`assemble()`、源码扫描归属 |
| 提示词 | 模型收到的提示词由哪些段落拼成 | `systemPrompt.layers`、`assemble()` |
| 预测 | 首条消息发出前模型会收到什么 | preset scope 的一次真实装配 |

做得好的四件事：

1. **组合链归因**：`layers → entries → 行 → 条目`，还区分了 bundle 覆盖与用户 patch（[layers.js](../lib/host/layers.js)、[entries.js](../lib/host/entries.js)）。
2. **名字级归属**：注册表不记 owner，就用源码扫描补（[source-scan.js](../lib/host/source-scan.js)、[attribution.js](../lib/host/attribution.js)）。这是本插件最有辨识度的能力。
3. **模型视角**：不只列注册表，还看 `assemble()` 与 session log，能回答「实际请求比预测多了什么」（[session-influence.js](../lib/host/session-influence.js)）。
4. **一个受控的写入路径**：模板 recipe + 每会话 activation，写入范围明确、可撤销（[materialize.js](../lib/host/templates/materialize.js)）。

但五个视图回答的都是**构造**问题。没有一个视图回答：

> 「过去 24 小时，这个插件实际做了什么？它现在健康吗？如果我把它关掉，会发生什么？」

代码层面的几个直接证据：

| 现象 | 代码位置 |
|---|---|
| 配置只收集字段名，没有值 | [entries.js](../lib/host/entries.js) 的 `configKeys` |
| 会话事件读到了，但没有归约 | [session-influence.js](../lib/host/session-influence.js) 的 `summarizeSessionEvents` 只处理请求形状，`tool/call` / `tool/result` 只计数 |
| 源码扫描只覆盖工具与提示词 | [source-scan.js](../lib/host/source-scan.js) 只有 `defineTool` / `systemPrompt.*` 四类模式 |
| 没有插件级控制路由 | [index.js](../lib/index.js) 的八条路由里没有 enable/disable |
| 快照只取一次，手动刷新 | [client.store.js](../lib/client.store.js) 的 `useSnapshotStore` |
| 插件详情只有六段静态事实 | [client.plugins.js](../lib/client.plugins.js) 的 `Detail` |

## 2. 用户对一个插件能看到的信息，够不够？

### 2.1 维度对照

| 维度 | 现在能看到 | 缺口 |
|---|---|---|
| 身份 | 条目 id、Loader id、模块、包名、版本、目录、描述 | 基本足够 |
| 来源 | 层、行、覆盖者、用户 patch | 基本足够 |
| 状态 | 有效启用、禁用表达式、fiber 阶段、失败诊断、配置字段名 | 有诊断，但没有健康汇总、没有历史 |
| 组合链 | 层 → 行 → 条目 | 足够 |
| 依赖 | 服务需求/提供、客户端模块声明 | `ctx.get()` 软依赖不可见；`intercept/isolate` 不可见 |
| 能力面 | 工具名、提示词段名、副作用标签 | 没有路由、槽位、命令、事件、投影、Remote 方法；客户端半几乎不可见 |
| 配置 | 配置字段**名** | 没有值、来源层、默认值、schema；也没有脱敏策略 |
| 行为 | `fiber.getEffects()` 的登记标签 | 这是「登记了什么」，不是「实际发生了什么」 |
| 影响 | 直接服务供需 | 没有反向影响、没有「禁用它会失去什么」、没有会话/模式影响面 |
| 证据 | README 里写了出处 | 界面不展示证据等级、覆盖率、未知项 |
| 时间 | `generatedAt` | 没有快照差分、没有变更历史、没有「自上次打开以来变了什么」 |

### 2.2 能力面只到「名字」，没有「面」

现在插件详情里的「行为」把 effect 标签树按类别归并成计数（不展开原始标签），能看出「注册工具 / 监听事件 / 提供服务」，但不能回答：

- 这个插件挂了哪些 **HTTP 路由**、**界面槽位**、**命令**、**Remote 方法**、**会话投影**？
- 它监听了哪些事件？哪些事件只是 `ctx.on('x')`，没有出现在 `inject` 里？
- 它的浏览器半声明了哪些 chunk、挂到了哪些 slot？现在只显示「双面 / host」和 `client.inject`，看不到实际界面贡献。
- 它在 `apply()` 里用 `ctx.get('x')` 软取了哪些服务？README 已把它列为已知边界，但用户看不到「这里可能少了一根依赖」。
- 它有没有用 `ctx.intercept()` / `ctx.isolate()`？README 说不反射私有结构，这是对的；但源码扫描可以给出「源码声明了这类手段」的**低置信度**提示，而不是完全沉默。

**建议**：把「行为」升级为「能力面（surface）」：服务、工具、提示词段、路由、槽位、命令、事件、投影、Remote 方法、客户端 chunk 各一栏；每项可点、可跳转；区分「运行时实测」「源码扫描」「未识别」三种证据等级。

### 2.3 配置只到「键」，没有「值」和「来源」

[entries.js](../lib/host/entries.js) 只把 `Object.keys(options.config)` 放进快照。用户能看到「这个插件有 5 个配置字段」，但看不到：

- 每个字段现在是什么值（以及哪些值被脱敏）；
- 这个值来自 bundle 默认、home patch、profile patch 还是运行时覆盖；
- 字段的默认值、类型、是否必填；
- 哪一层覆盖了哪一层。

这不是「信息不够多」，而是**最影响行为的那一半信息没有出界面**。建议先做「生效值 + 来源层 + 脱敏」，schema/default 作为下一阶段（运行时不一定有公开的 schema 读取面，需先验证 `fiber.runtime?.Config` 是否可作为稳定入口，或从包 README / config catalog 补）。

### 2.4 行为只到「登记」，没有「发生」

`fiber.getEffects()` 是框架给的元数据，可信，但它描述的是**注册动作**：

```
tools.register 61
ctx.on 135
ctx.provide 78
```

用户真正想知道的是：

- 这个插件注册的 `read` 工具过去 7 天被调用了多少次？失败率多少？p95 多长？最后一次是什么时候？
- 它的提示词段每轮注入多少字节？占系统提示词的百分之几？
- 它有没有在某个会话里报错，但 fiber 还是 active？
- 它是不是「装着但从来没用过」？

这些都不需要插件改造：**session log 里已经有 `tool/call`、`tool/result`、`system/message`、`user/message`、`request/header`、`*-llm-request`**。当前 [session-influence.js](../lib/host/session-influence.js) 只处理请求形状，`tool/call` / `tool/result` 只被计数，没有被归约。这是最便宜的突破口。

### 2.5 影响只到「直接依赖」，没有「如果我动它」

服务供需是列出来的，但用户要的是：

- 如果我禁用这个插件，哪些工具会消失？哪些提示词段会消失？
- 哪些插件会因为失去必需服务而停在 pending？
- 哪些模式、哪些活会话会受影响？全局还是单会话？
- 有没有别的提供者顶上？

这些数据大部分已经在快照里（工具归属、段归属、`services` 的 providers/consumers、模式行、活会话运行时），缺的是一个**反向索引 + 差分算法**。

### 2.6 证据与未知没有出界面

README 写得很清楚：哪些是运行时事实、哪些是声明值、哪些是源码扫描、哪些是推断。但界面里只有一个静态详情，用户看不到：

- 这个工具/段是「精确同名匹配」还是「模板匹配」还是「未归属」；
- 本机 62 个工具归属 61 个、10 个段归属 8 个，这类覆盖率数字；
- 哪些条目是模式合成条目、哪些 effect 读不到、哪些会话没有运行时值。

**建议**：在详情末尾加「证据」栏，并在页头/筛选里显示「未归属 N 项」。这不是装饰，它决定了用户该不该相信当前页面。

### 2.7 小结

> 信息不是「少」，而是**偏静态、偏结构、偏单点**。缺的是运行事实、时间维度、影响面和置信度。

## 3. 查看运作：现在只能「刷新一次，看一份快照」

| 能力 | 现状 | 用户的实际体验 |
|---|---|---|
| 自动更新 | 只有手动「刷新」 | 关了插件、改了配置，页面还是旧的 |
| 健康总览 | 无 | 209 行里自己找失败、缺服务、异常 |
| 活动时间线 | 无 | 只能去 session log 里翻 |
| 跨会话聚合 | 无 | 不知道哪些插件真的在被用 |
| 变更记录 | 无 | 不知道「昨天还好，今天怎么坏了」 |
| 快照差分 | 无 | 无法回答「自上次打开以来变了什么」 |
| 导出/诊断包 | 无 | 报 bug 只能截图 |

一个具体的证据：会话日志里已经有足够多的运行事实——

```
tool/call        5    工具名、参数、时间
tool/result      5    结果、isError、时间
system/message   1    最终系统提示词
user/message     2    runtime-context / time-context / skill-catalog
request/header   1    最终工具名集合
*-llm-request    1    标题/压缩等额外 LLM 请求
```

但插件控制台只把它们用于「这个会话的请求长什么样」，没有做**按插件的聚合**。所以「查看运作」这件事目前是缺位的，不是数据缺位。

## 4. 控制：现在只有「改提示词和工具」

README 的边界写得很明确：不启用/停用任何插件，也不改 profile 的 yml。这本身是对的——全局启停是 `pluginManager` 的职责。但站在用户目标「更自主、更简便地控制 DSH 插件」上，现状有三个问题：

1. **只有一条写入路径**：模板 recipe 只能改提示词段和工具 deny，不能碰插件本身；每会话开关也只控制模板是否生效。
2. **没有「先看影响再动手」**：即便用户去 plugin-manager 关插件，也看不到「关掉它会失去哪些工具/段、哪些会话会受影响」。
3. **没有审计与撤销**：关了之后没有记录「谁在什么时候关的、之前是什么状态」，也没有一键恢复。

另外，现有 [materialize.js](../lib/host/templates/materialize.js) 已经具备两个关键能力：

- 同名 section 覆盖（空字符串 = 隐藏该段）；
- `tools.restrict({ deny })` 黑名单。

这意味着**「会话级屏蔽某个插件的贡献」在技术上已经可行**，只是还没有产品化。它比全局禁用安全得多，也正好补上「简单控制」的空缺。

## 5. 建议的新方向：三层控制台

### 5.1 定位与边界

| 包 | 负责 | 与插件控制台的关系 |
|---|---|---|
| `plugin-manager` | 安装/移除、bundle 启停、条目启停、profile patch | 全局变更的**唯一执行者**；插件控制台调用它，不自己写 patch |
| `host-plugin-inventory` | 只读的 Loader 投影 | 原始清单；插件控制台在其上做归因、行为、影响 |
| `dsh-plugin-console` | 解释组合、观测运行、做**会话级可撤销调节** | 本次要升级的主体 |

一句话边界：

> **全局变更只调用 `pluginManager`；会话级变更只做「贡献掩码」，不假装卸载插件。**

### 5.2 信息架构：五个视图 + 一个「运行」页

不建议把控制做成第七、第八个标签。建议保持「一页一个问题」，只加一个：

```
插件   这台机器装了什么
运行   最近怎么样、哪里不对、变了什么   ← 新增
会话   这个会话的插件是哪来的、它们参与了多少
工具   模型能看到哪些工具、谁给的、用了多少
提示词 模型收到的提示词由哪些段落拼成、谁写的
预测   首条消息发出前模型会收到什么
```

页头加一条**健康条**（不是一排胶囊）：

```
失败 2 · 缺服务 1 · 未归属 7 · 快照 3 分钟前 · [自动刷新 ✓]
```

插件详情重新排序，按用户任务而不是按数据源：

| 顺序 | 段落 | 内容 |
|---|---|---|
| 1 | 健康与最近活动 | 状态、最后使用、调用数、错误率、p95、最近错误 |
| 2 | 能力面 | 服务/工具/段/路由/槽位/命令/事件/投影/Remote/客户端 chunk |
| 3 | 组合链与状态 | 现有的来源、覆盖、禁用表达式、fiber 阶段 |
| 4 | 配置 | 生效值、来源层、脱敏、默认值（有则显示） |
| 5 | 影响 | 反向依赖、「禁用它会发生什么」 |
| 6 | 行为 | 现有 effects，但按能力面归类，不再是一棵难读的标签树 |
| 7 | 证据 | 数据来源、置信度、未归属项、已知盲区 |

默认只展开 1~3；4~7 折叠。这样既保留深度，又不把详情撑成文档。

### 5.3 轨迹层：不要求插件改造的活动追踪

#### 数据来源

| 事实 | 来源 | 用途 |
|---|---|---|
| 工具调用 | `tool/call` 的 `name` / `time` / `callId` | 调用量、最后使用 |
| 工具结果 | `tool/result` 的 `isError` / `time` | 错误率、端到端耗时 |
| 提示词注入 | `system/message` 长度；`user/message` 的 `source.kind` | 每轮注入字节、注入次数 |
| 运行时上下文 | `source.kind = runtime-context` 的 sections | 谁在往上下文里加东西 |
| 额外 LLM 请求 | `*-llm-request` 的 provider / route / maxTokens | 标题、压缩等隐性成本 |
| 会话归属 | header 的 preset / workspace / parentSession | 影响面 |
| 变更 | `plugin-manager/changed`、`plugin-manager/operation`、快照差分 | 审计与「什么时候变的」 |

#### 指标

按 **插件 / 工具 / 会话** 三个粒度聚合：

| 指标 | 定义 | 注意 |
|---|---|---|
| `calls` | `tool/call` 次数 | 只覆盖工具型贡献 |
| `errors` | `tool/result.isError` 次数 | 包含参数错误，不等于插件 bug |
| `errorRate` | errors / calls | 样本太小时不显示百分比 |
| `p50/p95` | `tool/call → tool/result` 的墙钟时间 | 端到端代理，不是插件内部 CPU 时间 |
| `lastUsed` | 最后一次调用/注入时间 | 判断「装着但没用」 |
| `sessions` | 出现的不同会话数 | 影响面 |
| `injectedBytes` | 系统提示词/上下文贡献的字节 | 上下文成本 |
| `auxRequests` | 额外 LLM 请求数 | 隐性调用 |

关于 `injectedBytes` 的精度：`system/message` 是拼接后的整串，按插件拆分只能用注册表/`assemble()` 的段长做**静态归属**；`runtime-context` / `time-context` / `skill-catalog` 这类 `user/message` 带 `source.sections`，可以按块精确归属。两者要在界面上分开标，不要把静态段长说成「这一轮实际注入」。

#### 归属

- 工具名 → 行：复用 [attribution.js](../lib/host/attribution.js) 的 `toolOwners` / `mcpServerRow`；
- 段名 → 行：复用 `sectionOwners`；
- `source.kind` → 包：扩展现有 `SOURCE_OWNERS` 映射；
- 额外 LLM 请求 → 包：按 provider 映射；
- **未归属单独成桶**，不要隐藏。界面上显示「未归属 N 次调用」，这本身就是诊断信息。

#### 诚实的覆盖范围

这项能力是**贡献形状**的，不是万能的：

- 工具型、提示词型、注入型插件：可观测；
- 只提供服务、只监听事件、只在后台做事的插件：session log 里没有它们的「调用」，只能看健康状态与副作用登记，不能编造活动。
- 所以「活动」栏要明确写「未观测到活动 ≠ 没有运行」。

#### 健康模型

不要用红/绿二元状态，建议五档：

| 状态 | 判定 | 用户动作 |
|---|---|---|
| 正常 | active，无缺服务，错误率低 | 查看 |
| 异常 | failed、缺必需服务、错误率/延迟明显偏高 | 看诊断、考虑禁用/掩码 |
| 条件 | 被表达式禁用、条件未满足 | 看条件、决定是否启用 |
| 未激活 | 无活 fiber、冷会话、模式未挂载 | 看声明值，不当作故障 |
| 未使用 | active 但 30 天无活动（仅对有活动面的插件） | 考虑移除，但不自动判定 |

「未使用」是信息，不是告警。不要把「没调用」说成「坏了」。

#### 时间线与变更

- **活动时间线**：全局 / 单插件 / 单会话三种入口；按时间倒序，支持按插件、类型（工具/注入/错误/控制）、严重度筛选；每行可跳到对应会话影响页。
- **变更记录**：快照差分（新增/移除/版本/phase/启用状态/工具/段/服务/配置哈希）+ 控制审计 + `plugin-manager/changed`。回答「自上次打开以来变了什么」。
- **实时**：优先订阅 `plugin-manager/changed`；活会话事件若有公开的 `session/event` 订阅面就用它，否则在面板可见时低频轮询 `snapshotEvents()`。不要为了实时而反射私有结构。

### 5.4 影响层：先算清楚，再动手

任何控制动作前，生成一份**影响预览**。算法全部基于现有快照，不需要新数据源：

1. 从快照建立四张反向索引：工具→所有者、段→所有者、服务→提供者/消费者、模式/会话→插件。
2. 对目标插件，取它的工具、段、服务。
3. 去掉目标后，找出**没有其他所有者**的工具/段（真正会消失的）。
4. 找出**唯一提供者**的服务，以及这些服务的消费者（会停在 pending 的插件）。
5. 找出声明了它的模式、运行时包含它的活会话、按模式推断的冷会话。
6. 按动作类型裁剪：全局禁用看全部；会话掩码只看该会话可见的工具/段；配置修改看受影响条目。
7. 返回结构化结果，UI 只负责展示。

示例输出（数字仅示意）：

```
禁用 dsh-tool-bash 会影响：
  工具：bash（无其他所有者）→ 标准模式 94 → 93
  服务：bashRuntime（唯一提供者）→ 2 个消费者会停在 pending
  模式：标准模式、创造者模式
  活会话：3 个；冷会话：12 个（按模式推断）
  生效：需要重启（当前无 HMR）
  可撤销：是（记录原状态）
```

这张表比任何「确定要禁用吗？」都有用。

### 5.5 杠杆层：分级控制

| 层级 | 动作 | 影响范围 | 生效时机 | 可逆 | 实现 |
|---|---|---|---|---|---|
| 会话 | **贡献掩码**：隐藏某插件的工具/提示词段 | 该会话 | 下一步 | 是 | 编译进 recipe，`restrict` + 空段覆盖 |
| 会话 | 临时禁用某工具 | 该会话 | 下一步 | 是 | 现有模板能力 |
| Profile | 启用/禁用条目 | 所有会话 | HMR 或重启 | 是 | `pluginManager.setPluginEnabled` |
| Profile | 启用/禁用 bundle | 所有会话 | HMR 或重启 | 是 | `pluginManager.setBundleEnabled` |
| 诊断 | bisect 向导 | 视步骤 | 立即/重启 | 自动恢复 | 组合上述 |
| 高级 | 改配置 / 重载 | 视条目 | HMR/重启 | 取决于 | 后续阶段 |

#### 会话贡献掩码

这是最值得先做的控制，因为它安全、即时、可撤销，而且不需要改 profile：

- 输入：目标会话 + 目标插件；
- 计算：该插件在该会话可见的工具、提示词段；
- 编译：把「模板 recipe」与「掩码」合并成**一份** session plan，再物化一次；
- 语义：只隐藏该插件的**注册贡献**，不卸载插件、不停服务、不移除事件监听；
- 诚实提示：服务、监听器、运行时上下文注入**无法**被掩码，界面要写明「这是贡献掩码，不是卸载」。

关键工程点：现有 `appliedHandles` 是「每会话一个句柄」。如果模板和掩码各自物化一次，会在同一个 scope 里重复注册同名段。必须先做**session plan 编译器**，把两者合成一份 recipe，再调用 `materializeRecipe`。冲突（模板要改某段、掩码要隐藏同一段）显式列出，不要让后者静默覆盖前者。

> 当前落地版本只做**工具掩码**；提示词段掩码涉及 `complete` 独占段与同名共享段，留待语义验证后再开。界面与 README 已如实标注。

三个必须如实处理的边界：

1. **重名贡献无法按所有者选择性隐藏**。工具注册表和提示词注册表都按名字索引；如果目标插件的 `grep` 与另一个插件的 `grep` 同名，`deny: ['grep']` 会同时挡掉两者，空段覆盖也会同时隐藏两家的同名段。影响预览要标出「共享名字」，并允许用户改为按工具名/段名精确选择，或直接拒绝。
2. **`complete: true` 的独占段不能简单置空**。极简模式的整份提示词就是一段 complete 段；把它覆盖成空字符串会让模型收到空提示词。遇到这种情况应拒绝掩码并说明原因，或走专门的 complete 语义替换。
3. **不认识的工具名要单独报告**。`restrict` 对当前 scope 不认识的全局名字会整批抛错；沿用现有做法，先过滤 `restrictableNames`，把没提交的名字列进 `skippedTools`，不要让整次掩码失败。

#### 全局启停

- 先调 `pluginManager.listPlugins()`，检查 `patchId` / `readOnlyReason`；`management-required` 或 `unaddressable` 的行直接禁用按钮并说明原因。
- 调 `setPluginEnabled(entryId, enabled)`；返回值可能是 `restart-required`、`overridden` 等，界面必须如实显示，不能假装已生效。
- 成功后重取快照，不要本地乐观更新。
- 不自己写 `cordis.patch.yml`，不复刻 plugin-manager 的 patch 比较逻辑。

#### 保护栏

- 控制默认收起，进入「操作模式」才出现按钮（与编辑器的「定制上下文」同一套思路）。
- 全局禁用：二次确认 + 影响预览 + 记录原状态；核心/受保护插件要求输入名字确认。
- 执行前重取快照并比较摘要；快照已变则要求重新预览，避免基于旧状态动手。
- 一次只做一个动作；失败时报告哪几项没成，不自动跳转（复用现有 apply 的教训）。
- 所有动作写审计：谁、何时、什么范围、动作、前后状态、结果、是否需重启。
- 撤销：全局动作再调一次 `setPluginEnabled` 回原值；会话掩码重新编译并物化回原 plan；bisect 自动恢复。

#### 诊断向导（后续）

VS Code 的 Extension Bisect 是很好的类比：二分禁用扩展来定位问题。但 DSH 的全局启停影响所有会话，不能照搬「随便关一半」。建议：

- 优先用**会话掩码**二分（只影响目标会话，安全）；
- 只有服务型/监听型插件才退到全局启停；
- 每一步都记录、可恢复；
- 明确告诉用户「这一步影响哪些会话、是否需要重启」。

### 5.6 证据层

- 每个数据块标注来源：`运行时实测` / `声明值` / `源码扫描` / `推断` / `未知`。
- 页头显示「未归属工具/段 N 项」「无运行时值的会话 N 个」。
- 提供「复制诊断包」：快照摘要（脱敏）+ 健康问题 + 最近活动 + 控制审计 + 版本信息；默认不含提示词全文、工具参数、工具结果。
- 可选：生成一段 Markdown 诊断报告，方便贴给 Agent 或提交 issue。

## 6. 技术落点

### 6.1 新模块（保持现在的分层与 1000 行上限）

| 模块 | 职责 |
|---|---|
| `host/activity.js` | 从 session log 归约工具调用/注入/错误，按会话缓存 |
| `host/health.js` | 健康模型、注意力列表、未知项统计 |
| `host/impact.js` | 反向索引、禁用/掩码的 what-if 差分 |
| `host/changes.js` | 快照摘要、差分、变更记录 |
| `host/control.js` | `pluginManager` 调用、保护栏、审计、撤销 |
| `host/session-plan.js` | 模板 recipe + 掩码 → 单一 session plan |
| `host/routes/activity.js` | `GET /api/plugin-console/activity` |
| `host/routes/impact.js` | `GET /api/plugin-console/impact` |
| `host/routes/control.js` | `POST /api/plugin-console/control` |
| `host/routes/changes.js` | `GET /api/plugin-console/changes` |

新模块仍然遵守现有依赖方向：`routes/* → host/* + templates/*`，不反向依赖。

### 6.2 快照增量

在现有 `readSnapshot()` 返回值上增加（不要把所有活动塞进主快照）：

- `health`: 失败数、缺服务数、未归属数、未使用数、异常条目 id；
- `attention`: 排序后的前 N 条问题；
- `changes`: 与上一次摘要的差分（或单独路由懒取）；
- `entries[].surface`: 结构化能力面（路由/槽位/命令/事件/投影/Remote）；
- `entries[].config`: 生效值 + 来源 + 脱敏标记；
- `entries[].health`: 单条目的健康档位与原因；
- `entries[].usage`: 最近调用数/错误率/最后使用（可懒加载，默认只给摘要）。

活动与影响不要进主快照：209 个条目 × 30 天日志会把响应撑大。用独立路由按需取。

### 6.3 存储

现有四张表（`templates` / `revisions` / `manifests` / `activations`）不动；新增：

| 表 | 内容 |
|---|---|
| `operations` | 控制审计：时间、范围、目标、动作、前后状态、结果、是否重启 |
| `snapshots` | 最近 N 份摘要（哈希 + 差异），用于「自上次以来」；可选 |

活动聚合默认**不持久化**：启动时按最近窗口重算，活会话增量更新。若后续需要跨重启，再按 `sessionId + lastSeq` 存紧凑聚合。

### 6.4 性能

- 活动路由必须带 `since` / `sessionId` / `pluginId` / `limit`；默认最近 7 天、最多 20 个会话。
- 每个会话按 `lastSeq/time` 缓存；只读新增事件，不重复解析整份日志。
- 冷会话读日志有上限；超限时返回「已扫描 N 个会话」而不是静默截断。
- 健康总览只做轻量计算；详细错误样本按需展开。
- 工具 schema 已经很大，活动/影响不要重复携带。

### 6.5 隐私与安全

- 活动默认只存**元数据**：工具名、状态、耗时、时间、会话 id；不存参数和结果。
- 错误样本按需读、展示前截断/脱敏；不写进审计，不进导出包。
- 配置值按 key 名脱敏（`key`、`token`、`secret`、`password`、`authorization` 等）。
- 控制路由沿用 `connection.fetch` 的鉴权；全局动作要二次确认 + 审计。
- 不给模型无保护的控制权；若未来加 Agent 工具，必须沿用 `plugin_manager` 的审批语义。

### 6.6 测试

沿用现有 verify 风格，新增：

| 脚本 | 证明什么 |
|---|---|
| `verify-activity.mjs` | 合成 tool/call/result、injection 事件，聚合数字正确；未知归属进未知桶 |
| `verify-impact.mjs` | 固定快照下，禁用某插件时丢失的工具/段/服务/会话计算正确 |
| `verify-control.mjs` | 受保护/不可寻址条目拒绝；`restart-required` 如实返回；审计写入 |
| `verify-changes.mjs` | 两份快照的 added/removed/changed 正确；无变化时不造假 |
| `verify-session-plan.mjs` | 模板 + 掩码合并为一份 recipe，无重复注册；冲突被列出 |
| `verify-export.mjs` | 导出包不含提示词全文、工具参数、未脱敏配置 |

## 7. 路线图

| 阶段 | 交付 | 风险 | 验收 |
|---|---|---|---|
| **P0 快速见效** | 健康条 + 注意力列表；自动刷新/陈旧标记；快照差分；插件行显示调用数/错误率/最后使用；工具页加使用列 | 低 | 打开面板 10 秒内能说出「哪里不对、哪些没用、变了什么」 |
| **P1 轨迹与详情** | 「运行」页（健康/活动/变更）；插件详情重排 + 能力面 + 配置值 + 影响；会话参与情况；活动路由与缓存 | 中（日志读取量、归属盲区） | 不离开面板就能回答「它最近做了什么、影响了谁」 |
| **P2 分级控制** | 操作模式；会话贡献掩码；全局启停（调用 pluginManager）；影响预览；审计/撤销；保护栏 | 中高（误操作、HMR 语义） | 关一个插件/掩码一个插件，能看到影响、执行、审计、撤销全链路 |
| **P3 诊断增强** | bisect 向导；doctor 规则；配置编辑/重载；诊断导出；可选 Agent 工具 | 高（影响面、复杂度） | 能从「某个会话坏了」走到「定位到插件并恢复」 |

建议顺序：**P0 先做「快照差分 + 健康条 + 工具活动列」**。前两件不需要新数据源；第三件只需要一个从 session log 归约 `tool/call` / `tool/result` 的小模块。它们能把「运行」这件事从 0 变成 1。P1 再做详情与运行页，P2 才碰控制。

## 8. 边界与风险

- **不要做第二个 plugin-manager**：安装/移除/bundle 选择继续交给它；插件控制台只做解释与分级调节。
- **全局控制有爆炸半径**：所有会话共享 profile；必须显示范围、生效时机、重启要求，并提供撤销。
- **会话掩码不是卸载**：服务、监听器、运行时上下文注入不能靠掩码去掉；界面必须写明。
- **活动覆盖不完整**：只服务/只监听的插件没有「调用」可统计；不要用 0 活动推断故障。
- **归属盲区**：源码扫描有上限（文件数/字节/模式），MCP 工具靠名字规则；未知项要显示，不要硬凑。
- **性能**：不要在快照里塞全量活动；不要把 30 天日志一次读进内存。
- **隐私**：默认不存参数/结果/提示词全文；导出包必须脱敏。
- **实时性**：优先公开事件（`plugin-manager/changed`），其次低频轮询；不要反射私有结构。
- **UI 复杂度**：最多加一个「运行」页；控制按钮上下文出现，不做一排常驻开关。

## 9. 成功标准

用「用户问题 → 回答时间」衡量，而不是用功能数量：

| 用户问题 | 现在 | 目标 |
|---|---|---|
| 这个插件是哪来的？ | 已很好 | 保持 |
| 它最近做了什么？ | 无法回答 | 10 秒内，看活动栏 |
| 它现在健康吗？ | 要自己翻 209 行 | 3 秒内，看健康条/详情首段 |
| 哪些插件装了但没用？ | 无法回答 | 10 秒内，按最后使用排序 |
| 如果我禁用它会怎样？ | 无法回答 | 5 秒内，看影响预览 |
| 我刚才改了什么？怎么撤回？ | 无法回答 | 打开变更记录，一键撤销 |
| 这个结论可信吗？ | 只能读 README | 详情里看证据等级与未归属项 |

如果这七个问题都能在面板里闭环，它就从「插件地图」变成了真正的「插件运行控制台」。

## 10. 改进之后，具体能得到什么效果

一句话：**从「能看见构造」变成「能回答运行问题，并且敢做一点改变」。**

### 10.1 用户任务的前后对比

| 任务 | 现在要做什么 | 改进后 | 实际收益 |
|---|---|---|---|
| 找出哪个插件在报错/变慢 | 翻 209 行找失败标记，再去 session log 搜 | 健康条 + 注意力列表直接列出条目、错误率、最近错误 | 从「分钟级翻找」到「一眼看到」 |
| 判断哪些插件装了没用 | 无法判断，只能猜 | 按调用数/最后使用排序；30 天无活动的插件单独标出 | 清理有依据，不怕误删常用的 |
| 关一个插件前评估影响 | 凭经验，或者关了再看 | 影响预览：失去哪些工具/段/服务，影响哪些模式和会话，是否要重启 | 从「赌一把」到「先看后果」 |
| 排查某个会话少了工具/段 | 插件页、会话页、工具页、日志四处对照 | 会话详情直接给「本会话参与情况 + 与基线差分 + 变更记录」 | 一个页面闭环 |
| 回滚一次改动 | 不记得之前是什么状态 | 变更记录 + 一键撤销（全局回原状态，会话掩码回原 plan） | 敢试，因为能撤回 |
| 看插件到底改了什么提示词/加了什么上下文 | 提示词页看静态段，session log 看最终文本 | 活动时间线按插件归因注入，静态段长与每轮实际注入分开显示 | 知道「谁把上下文撑大了」 |
| 给插件作者报问题 | 截图 + 口述 | 一键导出脱敏诊断包：组合、健康、活动、版本、审计 | 作者能复现，来回少几轮 |
| 评估新装插件是否值得留 | 装完用几天，凭感觉 | 试用期看调用数、错误率、注入字节；不满意用会话掩码先关掉 | 试用成本低，决策有数据 |

### 10.2 一个具体场景：某个会话突然不对劲

**现在：**

1. 打开插件页，在 209 行里找失败、缺服务、被覆盖；
2. 打开会话页，看它用的是哪个模式；
3. 打开工具页，对比全局、模式层、会话层；
4. 去 session log 里翻 `tool/call` / `tool/result`；
5. 猜是哪个插件；
6. 去 plugin-manager 全局关掉，可能还要重启，再试；
7. 忘了刚才关了什么，回滚靠记忆。

**改进后：**

1. 打开「运行」页，注意力列表直接写：
   「会话 `session-…` 最近 3 次 `tool/result` 报错，归属插件 `dsh-tool-bash`；错误 `PTY shell exited during startup`」；
2. 点插件，看到最近活动、错误样本、影响面；
3. 对这个会话做**贡献掩码**，下一步生效，不影响其他会话；
4. 观察一轮；不行就一键撤销；
5. 确认是插件问题后，再决定要不要全局禁用/升级/反馈作者。

差别不只是「快」，而是**先在小范围验证，再决定要不要扩大影响**。这是「更自主、更简便」的核心。

### 10.3 一个具体场景：插件大扫除

**现在：** 209 个插件，不知道哪些是必需的、哪些是装了没用的；想删又怕删错；删了出问题只能重装。

**改进后：**

- 按「最后使用」排序，直接看到「30 天没调用过、但注册了 3 个工具」的候选；
- 点开影响预览，看到「禁用后标准模式 94 → 93，无服务消费者，0 个活会话受影响」；
- 先会话掩码验证，再全局禁用；
- 每一步有审计，随时可撤销。

结果是：**插件清理从「高风险手工活」变成「有数据支撑的低风险操作」。**

### 10.4 工程上的效果

- **不重复造轮子**：全局变更继续走 `pluginManager`，插件控制台只做解释、观测、会话级调节；边界清晰，维护成本低。
- **快照仍然快**：活动、影响、变更走独立路由按需加载，不把 30 天日志塞进主快照。
- **可测试**：活动聚合、影响差分、控制保护栏、导出脱敏都能写成确定性的 verify 脚本，不靠人工点。
- **未知项可见**：未归属工具/段、无运行时值的会话、只服务/只监听的插件，都在界面上有明确位置；质量可以逐版本度量。
- **复用现有能力**：`materializeRecipe` 的段覆盖与 `tools.restrict`、`attribution` 的名字索引、`session-influence` 的日志读取，都是现成的，不需要重写。

### 10.5 对生态的效果

- **插件作者**：能拿到一份结构化的「我的插件贡献了什么、最近运行得怎么样、用户环境里哪里不匹配」的报告，比截图和口述有用得多。
- **用户**：装插件前能看能力面和影响，装完能看活动，出问题能安全回退；对「装插件」这件事的信任度会提高。
- **DSH**：插件控制台可以成为插件可观测性的参考实现；如果验证有效，活动/影响/审计的契约可以反哺宿主或 plugin-manager。

### 10.6 可量化的验收

| 指标 | 现状 | 目标 |
|---|---|---|
| 定位故障插件 | 分钟级，需翻日志 | < 1 分钟，注意力列表直达 |
| 判断插件是否在用 | 无法回答 | 10 秒内，按最后使用排序 |
| 关插件前的影响评估 | 无 | 5 秒内，影响预览 |
| 控制动作可撤销率 | 不适用 | 100%（全局/掩码都有记录） |
| 未归属项 | 只在 README 里 | 界面上可见，且随版本下降 |
| 诊断包 | 截图 | 一键导出，默认脱敏 |
| 全局禁用次数 | 排查时常用 | 更多改为会话掩码，影响面更小 |

### 10.7 不承诺什么

- **不是 APM**：只覆盖工具、提示词、注入这类「有事件」的贡献；只服务/只监听的插件没有调用活动，只能看健康状态。
- **不是自动根因**：doctor 是规则引擎，给的是「可能原因 + 证据 + 下一步」，不是断言。
- **不是真正卸载**：会话掩码只隐藏注册贡献，不停服务、不移除监听器；界面会明确写。
- **不替代 plugin-manager**：安装、移除、bundle 选择仍然是它的事；插件控制台只调用它。
- **不保证实时**：受公开事件与日志读取能力限制；没有公开订阅面时用低频轮询，不反射私有结构。
